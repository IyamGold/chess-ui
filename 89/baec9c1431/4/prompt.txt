# Use Stockfish WASM on Server (Same Engine as Frontend)

## Context
The server tries to spawn a native `stockfish` binary (fails — not installed). The frontend already has Stockfish compiled to WASM (`stockfish.js` npm package v10.0.2) working perfectly in the browser. We'll use the same WASM engine server-side via Node.js `worker_threads`.

## Why worker_threads?
The `stockfish.wasm.js` module is an Emscripten build targeting Web Workers — it uses `onmessage`/`postMessage` globals. Node.js `worker_threads` is the direct equivalent. A thin adapter script (~15 lines) shims those globals.

## Changes

### 1. New file: `server/chess/stockfishWorker.js` (~15 lines)
Adapter bridging Web Worker API → Node.js worker_threads:
- `global.postMessage` → `parentPort.postMessage()`
- `global.close` → `process.exit()`
- `parentPort.on('message')` → `global.onmessage({ data })`
- Set CWD to the stockfish.js package directory (so it finds `stockfish.wasm`)
- `require('stockfish.js')` at the end — loads and auto-initializes

### 2. Modify: `server/chess/stockfishPlayer.js`
Swap `child_process.spawn('stockfish')` → `new Worker('./stockfishWorker.js')`:
- `this.process.stdin.write(cmd)` → `this.worker.postMessage(cmd)`
- `this.process.stdout.on('data', fn)` → `this.worker.on('message', fn)`
- `this.process.kill()` → `this.worker.terminate()`
- Same public interface: `init()`, `getBestMove(fen, level)`, `terminate()`

### 3. No other files change
`createStockfishPlayer()` factory and interface stay identical. Routes, index.js untouched.
